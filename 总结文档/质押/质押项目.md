# 质押

- 质押是指将一定数量的加密货币锁定在区块链网络中，以获得网络奖励或其他收益。
- 质押通常用于权益证明（Proof of Stake, PoS）机制的区块链网络中，参与者通过质押代币来获得验证交易和维护网络安全的权利。
- 质押的收益通常以额外的代币形式发放，收益率取决于网络的规则和质押的数量。
- 质押通常有锁定期，在此期间质押的代币无法自由转移或交易。
- 质押风险包括网络风险、智能合约风险以及代币价格波动风险。
- 参与质押前，用户应充分了解相关风险，并根据自身风险承受能力进行决策。

> 整体上这个合约本质上是一个“按区块线性发放奖励的多池质押合约”，很像 MasterChef / farming 体系，但做了有些定制化改动，比如“解除质押必须排队、需等待解锁区块”等。

一、整体定位：它解决什么问题？

这个合约的核心目标是：

- 用户把代币质押进池子里
- 按照“质押量 × 时间”来累计奖励
- 奖励代币是 MetaNode（ERC20）
- 奖励分配不是简单按用户数量算，而是按“池子权重”以及“每个池子里总质押数量”来计算
- 用户可以：
- 质押
- 解除质押（创建请求）
- 在锁定期结束后提取本金
- 领取奖励

简单说，它是“质押 + 奖励 + 解押锁定 + 分池权重”的组合。

二、关键数据结构

1. Pool：每个质押池的元数据

Pool 包含：

- stTokenAddress：该池的质押币地址
- 0 地址表示原生 ETH
- 非 0 表示 ERC20
- poolWeight：池子的奖励权重
- 比如 A 池权重 50，B 池权重 100，那么 B 池拿到更多奖励
- lastRewardBlock：最后一次更新奖励的区块号
- accMetaNodePerST：累计每单位质押代币能分到多少奖励
- 这是最关键的“奖励指数”
- stTokenAmount：池内总质押数量
- minDepositAmount：最小存入金额
- unstakeLockedBlocks：解除质押的锁定区块数

也就是说，每个池都在维护自己的一组“奖励增长指数”。

1. User：用户在每个池中的状态

User 包含：

- stAmount：用户在这个池中的当前质押量
- finishedMetaNode：用户已经“结算过”的奖励基准值
- pendingMetaNode：用户待领取但尚未被清空的奖励
- requests：解除质押请求列表
- 每个 request 有：

- amount：要解除多少代币
- unlockBlocks：什么区块后可以提取
- 这很重要：解除质押不是立刻把币还给你，而是先生成一个“待解锁请求”，等到 unlockBlocks 到达后再 withdraw。

三、奖励系统的核心思想

- 这个合约的奖励计算逻辑非常典型：按“累计收益指数”来算。

- 核心公式大致是：

- 每个池的累计奖励指数 accMetaNodePerST 会随区块增长而增加
- 用户最终可领奖励：
- 用户奖励 = 用户质押量 × accMetaNodePerST - finishedMetaNode + pendingMetaNode
- 这套设计的意义是：

- 不是每次都按“当前区块减去上次记录”的增量去算
- 而是通过累计指数让历史收益可以被压缩成一个标量
- 当用户发生存款、领取、解除质押等行为时，系统再把“未结算收益”转成 pending 或算到 finished 中
- 这个思想和 MasterChef 很相似，只是它的实现是“每池独立维护累积系数”。

四、奖励发放区间如何计算

- 合约里有这些全局参数：
- startBlock：质押奖励开始区块
- endBlock：奖励结束区块
- MetaNodePerBlock：每个区块发多少 MetaNode
- totalPoolWeight：所有池权重总和

- 关键函数是：
- getMultiplier(from, to)

- 它返回的是：
- 在 [from, to) 这个区间内，应该发放的区块奖励数
- 但会被限制在 [startBlock, endBlock] 之间
- 也就是“有效奖励区间”中，不会超出启动/结束时间

- 核心逻辑是：
- 区间区块数 = to - from
- 奖励总量 = 区间区块数 × MetaNodePerBlock
- 每个池的奖励 = 总奖励 × poolWeight / totalPoolWeight

所以分配奖励时，不是“每个用户按比例分”，而是“每个池子按权重分配”。

五、池子更新：updatePool

- 最关键的函数是 updatePool(uint256 _pid)
-
- 它做的事情是：
-
- 判断当前区块是否大于上次更新区块
- 计算该池在这段时间应该拿到多少奖励
- 按池的 totalPoolWeight 分摊
- 如果池中 stTokenAmount > 0
- 令：
- accMetaNodePerST += poolReward × 1e18 / stTokenAmount
- 更新 lastRewardBlock = block.number
- 也就是说，池子的“累计收益指数”不是在用户操作时才动，而是每次有区块更新时就会推进。

这也是为什么在合约中很多地方都会先调用 updatePool()，确保“现在的奖励指数是最新的”。

六、用户存款：deposit / depositETH

- ETH 池
- depositETH()：
-
- 要求池 0 的 stTokenAddress 是 0 地址
- msg.value 必须 >= minDepositAmount
- 调用 _deposit(0, msg.value)
- ERC20 池
- deposit(pid, amount)：
-
- 要求 pid != 0
- 要求 amount > minDepositAmount
- 注意这里是 >，不是 >=
- 用户先调用 approve
- 合约内部 safeTransferFrom 用户的代币到合约
- 然后调用 _deposit(pid, amount)
- 内部 _deposit 的流程：
-
- updatePool(_pid)
- 如果用户已经有 stAmount
- 计算当前这段时间产生的累计收益：
- accST = user.stAmount × pool.accMetaNodePerST / 1e18
- 计算 pendingMetaNode = accST - finishedMetaNode
- 如果 >0，就把这些奖励累积到 user.pendingMetaNode
- 增加新质押金额到 user.stAmount 和 pool.stTokenAmount
- 更新 finishedMetaNode = user.stAmount × pool.accMetaNodePerST / 1e18
- 这里的关键点是：
-
- 存款不立即发奖
- 而是把“之前已经产生但未结算”的奖励存进 pendingMetaNode
- 真正发放发生在 claim() 时
- 这也解释了为什么用户存款后，奖励不一定马上到账，必须自己 claim

七、解除质押：unstake

- unstake(pid, amount) 的逻辑相对关键。
-
- 它先做：
-
- require(user_.stAmount >=_amount)
- updatePool(_pid)
- 计算 pendingMetaNode_ = user.stAmount × accMetaNodePerST / 1e18 - finishedMetaNode
- 如果有待领奖励，就累积到 user.pendingMetaNode
- 然后减少用户 stAmount
- 同时生成一个 UnstakeRequest：
- amount = _amount
- unlockBlocks = block.number + pool.unstakeLockedBlocks
- pool.stTokenAmount -= _amount
- 更新 finishedMetaNode = (user_.stAmount × pool.accMetaNodePerST) / 1e18
- 也就是说：
-
- 解除质押会立刻减少用户已质押金额
- 但本金不会立刻返回
- 而是进入“等待解锁队列”
- 用户的奖励也会先结算到 pending 中，不会直接转走
- 所以从状态机来说，用户在 unstake 之后：
-
- 还保留在池里，但质押量减少
- 还可能还没领取奖励
- 本金在锁定期内不可提取

八、提取本金：withdraw

- withdraw(_pid) 的逻辑是：
-
- 遍历用户的 requests 数组
- 如果 request.unlockBlocks <= block.number
- 说明已经到解锁区块，可以提取
- 累加这些请求的 amount
- 把已经解锁的 request 从数组中删除
- 把对应本金转回用户
- ETH 池用 _safeETHTransfer
- ERC20 池用 IERC20.safeTransfer
- 注意一个细节：
-
- 它在循环中遇到第一个 unlockBlocks > 现在区块数 的请求就 break
- 也就是“后续请求即使已到期，也不会再处理”
- 这意味着请求数组必须保持按时间顺序放置，且不能在中间打乱
- 这个设计其实本质上是“FIFO 的锁定队列”，对前端和业务层要特别注意。

九、领取奖励：claim

- claim(_pid) 的逻辑也很关键：
-
- updatePool(_pid)
- 计算当前可领：
- pendingMetaNode_ = user.stAmount × accMetaNodePerST / 1e18 - finishedMetaNode + pendingMetaNode
- 如果 >0
- user.pendingMetaNode = 0
- safeMetaNodeTransfer(msg.sender, pendingMetaNode)
- 最后重置：
- user.finishedMetaNode = user.stAmount × accMetaNodePerST / 1e18
- 这里是个很重要的设计模式：
-
- finishedMetaNode 表示“已经分配基准值”
- pendingMetaNode 表示“临时累积待领”
- claim 之后会把 pending 清空，且同步更新 finishedMetaNode
- 所以用户领取奖励之后，后续再产生新收益时，会按新的基准继续累积，而不会重复发。

十、MetaNode 代币发放机制

- 合约中定义了：
-
- IERC20 public MetaNode;
- 管理员可在初始化时传入奖励 token 地址，调用 initialize():
-
- initialize(_MetaNode,_startBlock, _endBlock,_MetaNodePerBlock)
- 奖励发放依赖合约本身持有足够的 MetaNode 余额。
-
- 安全转账函数：
-
- _safeMetaNodeTransfer(address_to, uint256 _amount)
- 它会检查当前合约余额：
-
- 如果要求发放的 amount > 合约余额
- 则只转出合约当前余额
- 否则正常发放 amount
- 也就是说：合约本身一旦没有足够奖励，用户只能拿到剩余余额，并不会 revert。这个点是运营层容易踩坑的地方。
-
- 十一、管理员功能与权限模型
-
- 这个合约使用了 OpenZeppelin 的 AccessControlUpgradeable。
-
- 角色：
-
- DEFAULT_ADMIN_ROLE
- ADMIN_ROLE
- UPGRADE_ROLE
- 初始化时，部署者会被授予这些角色。
-
- 管理员可执行的核心操作：
-
- setMetaNode：设置奖励代币地址
- pauseWithdraw / unpauseWithdraw：暂停/恢复提现
- pauseClaim / unpauseClaim：暂停/恢复领取
- setStartBlock / setEndBlock：调整开始/结束区块
- setMetaNodePerBlock：调整每区块奖励
- addPool：增加一个质押池
- setPoolWeight：调整池权重
- updatePool：调整池的最小质押/锁定时长
- 升级逻辑：UUPS upgrade
- 注意：这里的“质押”和“解除质押”本身并不是管理员控制，而是用户调用，也受全局 paused 控制。
-
- 十二、合约中最关键的状态机顺序
-
- 可以把它理解为以下状态流：
-
- 用户 deposit
-
- updatePool
- 如果原来已质押，则先将旧收益记入 pending
- 新质押量加入 user.stAmount
- finishedMetaNode 重新更新
- 用户 unstake
-
- updatePool
- 把当前可结算奖励转入 pending
- stAmount 减少
- 生成 unlock request
- finishedMetaNode 根据新 stAmount 重新计算
- 用户 claim
-
- updatePool
- 计算当前全部可领奖励
- 转 MetaNode
- 清空 pending，更新 finishedMetaNode
- 用户 withdraw
-
- 扫描请求数组
- 找到已到 unlockBlocks 的记录
- 转回质押主币（ETH 或 ERC20）
- 五个关键点串起来，它就是一个“区块奖励 + 累积收益指数 + 锁定取款”的质押系统。
-
- 十三、几个容易踩坑的边界/逻辑细节
-
- 结束区块后，updatePool 可能出现“lastRewardBlock 变得大于 endBlock”
-
- 这是文档里已指出的风险点
- 原因是 getMultiplier 会在 endBlock 处截断，但 lastRewardBlock 仍然被写成当前块号
- 后续再次 updatePool 可能会让区间反向，产生错误计算
- 池权重为 0 也可能被允许添加
-
- 但最终分配奖励时会除以 totalPoolWeight
- 如果 totalPoolWeight = 0，就会出问题
- 所以管理端必须保证总权重大于 0
- 质押金额最小值逻辑不完全一致
-
- ETH 池：要求 >= minDepositAmount
- ERC20 池：要求 > minDepositAmount
- 这是一个很典型的细节，前端和后端要统一
- reward token 余额不足时，不会 revert，而是最多转出当前余额
-
- 这可能导致“页面显示应得 X，链上实际只收到 Y”
- 因为 _safeMetaNodeTransfer 中的逻辑是“尽量转，转不完也不报错”
- 解除质押之后不自动领取奖励
-
- 用户必须单独 claim
- 这是设计意图，但对用户体验而言需要前端显式提示
- 十四、总结一句话
-
- 这个合约的设计核心可以概括为：
-
- 多池质押 + 区块奖励 + 累积收益指数 + 解除质押锁定 + 用户端按需 claim/withdraw
它的本质不是“直接把每个区块产生的奖励按用户质押量累加”，而是通过 accMetaNodePerST 这种“累计比例”做高效的分账。这个设计能减少重复循环计算，但也带来一些状态同步与边界条件问题，特别是 endBlock、提款锁定、奖励余额不足等细节。
